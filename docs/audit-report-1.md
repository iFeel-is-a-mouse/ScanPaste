## 1. 完整性检查

| # | 问题 | 严重度 | 建议 |
|---|------|--------|------|
| C1 | **撤消/重做空状态未定义**：用户无追加记录时点击 Undo，或 redo 栈为空时点击 Redo，系统行为未描述（静默忽略？toast 提示？按钮置灰？） | 中 | 补充按钮禁用逻辑：Undo/Redo 在对应栈为空时置灰禁用 |
| C2 | **扫描失败场景定义不足**："扫描失败时显示提示，允许重试"——但"扫描失败"未细分：相机初始化失败 vs 取景框内无二维码 vs 二维码无法解码 vs 二维码内容为空 vs 相机被其他应用占用。这些场景的提示内容、是否可重试、是否可回退都应不同 | 高 | 枚举失败场景及对应的用户提示和回退策略 |
| C3 | **追加内容格式边界**：QR 码内容包含特殊字符（如 emoji、控制字符、超长文本、Base64 编码）时如何处理？是否有最大追加长度？ | 中 | 定义文本追加的字符集约束和最大长度限制 |
| C4 | **文本编辑区初始状态**：首次启动编辑区为空还是有 placeholder 提示文字？ | 低 | 建议添加 placeholder "输入文本或点击追加按钮扫码录入" |
| C5 | **App 生命周期处理**：扫码中途来电/切后台/息屏后的恢复行为未定义——相机是否自动恢复？是否保留已识别但未追加的内容？ | 中 | 描述 onPause/onResume 时相机和编辑区的状态保持策略 |
| C6 | **追加后撤销再手动编辑的交互边界**：spec 说 Undo "仅对追加操作生效，不影响手动编辑的内容"，但如果用户追加一段文字后手动删除了部分文字，再执行 Undo——是按插入时的位置恢复还是报错？ | 高 | 定义追加内容与手动编辑混合场景下的 Undo 行为 |
| C7 | **包体积 < 10MB** 达成路径未说明：引入 CameraX + ML Kit 扫码库后 APK 体积通常 > 10MB。是否启用 AAB 分包？是否使用 Play Feature Delivery？是否采用 minify/R8？ | 中 | 说明包体积达成的技术手段，或放宽到 < 15MB |

## 2. 歧义识别 (Clarify)

| # | 歧义描述 | 位置 | 严重度 | 建议澄清 |
|---|---------|------|--------|---------|
| CL1 | **"字号随内容量自动缩放"算法模糊**：spec 2.1 "文本字号随内容量自动缩放"——是按字符数？按行数？按填充百分比？是连续缩放还是阶梯式？触发时机是每次文本变更吗？AC1 给出边界值 >20sp/≥12sp 但仍未说明缩放算法 | spec 2.1 / AC1 | **高** | 明确：① 基于文本行数还是填充率触发缩放；② 缩放是连续还是阶梯（如 24/20/16/12sp 四档）；③ 设定明确的行数阈值（如 ≤3行→24sp, ≤8行→20sp, ≤15行→16sp, >15行→12sp） |
| CL2 | **"无限撤销"与实际内存/性能矛盾**：spec 2.3 "可无限撤销直到没有更多追加记录"——"无限"用词不严谨，实际受内存限制。每次追加的 QR 内容可能很长，100 次追加 × 1KB = 100KB 尚可，但若 QR 内容是 base64 编码图片（可能 10KB+），1000 次追加 = 10MB 内存 | spec 2.3 | **高** | 设定撤销深度上限（如 50/100 次），或基于内存总量限制（如历史栈总大小 ≤ 2MB） |
| CL3 | **"取消/重做共用同一历史栈"语义矛盾**：标准 Undo/Redo 模式是 Undo 栈 + Redo 栈分离，spec 说"共用同一历史栈"——是指一个带指针的双栈（类似浏览器前进后退），还是指取消就是退栈、重做就是进栈？这与"取消操作正确撤销最近一次追加，可连续撤销"和"重做操作恢复被撤销的追加"是否一致？ | spec 2.3/2.4 | **中** | 澄清数据结构：建议改为标准的 Undo Stack + Redo Stack 分离，或明确说明"基于游标的统一历史栈"的工作方式 |
| CL4 | **"撤销后光标定位到被撤销文本的原插入位置"实现可行性存疑**：手动编辑可能改变文本长度和偏移量，"原插入位置"如何精确定位？如果原位置已被手动编辑修改甚至删除，光标该放在哪里？ | spec 2.3 | **中** | 建议简化：撤销后光标放在被撤销位置（记录插入偏移量），或者改为"撤销后光标定位到文本末尾"以降低复杂度 |
| CL5 | **AC1 中字号边界值来源不明**：">20sp"和"≥12sp"是否是用户体验验证过的值？按 Android 无障碍标准，正文建议 ≥ 14sp，12sp 偏小 | AC1 | 低 | 建议最小字号调整为 ≥14sp 以符合无障碍标准，或添加用户可调字号设置 |
| CL6 | **"追加按钮激活摄像头"的交互细节缺失**：是直接调用系统相机 App 还是内嵌取景框？如果是系统相机，某些 ROM 的相机不支持扫码模式怎么办？ | spec 2.5 | 中 | 明确扫码实现方案：① 使用 CameraX + ML Kit Barcode Scanning（推荐，内嵌取景框体验好）；② 或降级方案：调用第三方扫码 SDK |
| CL7 | **style-guide 中 EditorViewModel "按复杂度决定"引入歧义**：spec 明确有 undo/redo 管理、字号自适应、追加等逻辑，复杂度已达"需要 ViewModel" 的阈值，但 style-guide 写成可选会导致实现争议 | style-guide 3 | 低 | 建议改为"必须使用 ViewModel"，消除歧义，与架构原则中的 ">300行引入ViewModel" 阈值保持一致 |

## 3. 安全性检查

| # | 问题 | 严重度 | 建议 |
|---|------|--------|------|
| S1 | **相机权限拒绝引导不够具体**：AC7 仅说"显示引导提示"，未明确是否提供"前往设置"的系统跳转。Android 11+ 权限被"不再询问"后需引导至 Settings，但 spec 未覆盖此场景 | 中 | 设计权限拒绝场景下的完整 UX 流：首次拒绝 → 解释用途 → 再次请求 → 再次拒绝 → 引导至设置页面（带 Snackbar + Action） |
| S2 | **剪贴板数据无保护说明**：编辑区支持复制/粘贴，若用户扫码录入敏感信息（如身份证号、银行卡号），剪贴板内容可能被其他 App 读取。Android 10+ 已限制后台剪贴板访问，但 spec 未提及 | 低 | 在 spec 中标注"不处理剪贴板数据保护，依赖系统安全机制"，或在非目标中声明 |
| S3 | **无 INTERNET 权限声明缺失**：spec 6 声明"不联网"，但未在非功能需求中明确禁止 INTERNET 权限。依赖库可能传递引入网络权限 | 低 | 在非功能需求中添加"禁止 INTERNET 权限"，并在 Manifest 中显式 `tools:remove="android.permission.INTERNET"` |
| S4 | **ML Kit 扫码的初始下载行为**：ML Kit Barcode Scanning 首次使用需下载模型（~3MB），若在无网络环境下首次扫码会失败。spec 说"纯离线"但未处理此场景 | 中 | 在 spec 中补充：① ML Kit 模型首次需网络下载（与"纯离线"冲突，需修正）→ 要么改为离线可用的 ZXing，要么取消纯离线声明；② 或采用 AAB 打包将模型打进安装包 |
| S5 | **代码混淆未提及**：style-guide 未要求 minify/R8。对于生产级 App，即使离线也需要基本混淆（反编译保护） | 低 | style-guide 添加：release build 启用 minifyEnabled + proguard-rules.pro |
