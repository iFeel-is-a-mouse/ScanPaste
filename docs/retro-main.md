| 指标 | 数据 |
|------|------|
| 复杂度评估 | M 级（实际应更接近 L 级） |
| 执行阶段 | 9/11（跳过 constitution + 复盘） |

## 做得好的

1. **多 Agent 协作流畅** — coder、tester、auditor 均按时交付，0 次卡住
2. **Auditor 前置审计质量高** — 发现 4 项阻塞，全部在设计阶段解决
3. **Coder 设计文档详实** — design.md 含 9 个 ADR，可测试项清单 76 项
4. **最终 APK 构建成功** — 5.9MB，远低于 10MB 限制

## 做错了的

### ❌ 错误 1：复杂度评估偏低

**现象**：将项目评为 M 级（实际应在 M-L 边界）

**根因**：
- 我只看了代码量（300-600 行）和文件数（5-8），低估了 Android 项目特有的构建复杂度
- 没有考虑第三方库 API 版本兼容性风险（ZXing 4.3.0 API 与设计文档不匹配）
- 没有考虑无 Android 环境的测试降级问题

**后果**：跳过了 constitution 和复盘，导致流程不够严谨

### ❌ 错误 2：测试在无环境下形同虚设

**现象**：70 个单元测试 vs 42 个手动 UI 测试（0 个执行）

**根因**：
- tester 的委托任务中写了"这是纯代码审查+单元测试，不需要运行 Android 设备"
- 这个前提本身就是错的——Android App 的核心价值在 UI 交互，不在 ViewModel 逻辑
- main 在审查 tester 报告时没有指出这个 gap

**风险敞口**：
- 扫码流程未实测（ZXing API 在构建时才暴露不兼容） ← 最高风险
- 权限引导流未实测
- 字号自适应在真机上的效果未验证
- 按钮防抖/键盘策略未实测

### ❌ 错误 3：构建环境问题本可避免

**现象**：源码有 2 处构建错误，需要 main 在构建阶段修复

1. `settings.gradle.kts` — `dependencyResolution` 应为 `dependencyResolutionManagement`
2. `QrCodeScanner.kt` — ZXing 包名从 `com.journeyapps.barcodescanner` 变为 `com.google.zxing.integration.android`
3. `themes.xml` — 需要简化以兼容 AGP 8.7

**根因**：
- coder 在编写代码时引用了过时的 ZXing API（可能是记忆/训练数据中的旧版本）
- auditor 终审没有检查"可构建性"
- tester 没有实际编译验证

### ❌ 错误 4：主教练通报频率不足

**现象**：从 00:06 到交付，iFeel 在 00:23 主动问"进展"

**根因**：
- main 在等待 agent 完成时进入了 yield 状态，没有主动通报
- "每 5 分钟通报"的规则在 yield 等待期间没有遵守
- iFeel 在 00:23 主动询问——这说明我沉默了 17 分钟

## 流程改进建议

### 对 team-dev SKILL.md 的修改建议

1. **M 级不应跳过复盘** — 复盘应该是必选项，S/M/L 都应执行
2. **增加"可构建性"检查** — auditor 终审 checklist 应包含编译验证
3. **无环境测试策略** — 应定义：什么情况下必须有真机/模拟器，什么情况可降级为代码审查
4. **复杂度评估应加"构建复杂度"维度** — Android/iOS/嵌入式项目天然比纯脚本复杂
5. **通报规则应覆盖 yield 等待期** — 等待 agent 期间也应在固定间隔发送状态

### 对自己（main）的改进

1. **复杂度评估要保守** — 宁可偏高一级，不可偏低
2. **tester 委托要明确"必须有运行环境"还是"可降级"**
3. **构建是审计的一部分** — 不能假设源码可编译就跳过
4. **不要跳过复盘** — 复盘比 spec 还重要
