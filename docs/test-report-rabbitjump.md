## 测试项逐项验证

### 1. 初始速度 = 0.5 ✅ / ⚠️
- **代码位置**：全局声明 `let ..., speed=0.5, level=1;`（第36行）
- **验证**：全局初始值确实为 0.5
- **问题**：`init()` 函数内**没有**重置 `speed`，依赖外部调用者在死亡时手动设置 `speed=0.5`。通关后（win→init）`speed` 会保留上一关的值，这是预期行为；但 `init()` 的职责不完整——它应当明确管理自己的状态。当前通过碰撞处理硬编码 `speed=0.5` 来弥补，属于**逻辑分散**。

### 2. 跳跃距离 = 5 ✅
- **代码位置**：`update()` jump 分支内 `const dist=5;`（第67行）
- **验证**：跳跃位移固定为 5 格，分 4 帧完成（`JUMP_FRAMES=4`），每帧插值 `t = jumpFrame/4`
- **计算**：落地位置 `rabbitPos = jumpStartPos + 5`，与代码一致

### 3. 碰撞检测逻辑 ⚠️ / 🔴
- **代码位置**：
  - walk 状态（第52行）：`if(rabbitPos>=FOX_POS&&rabbitPos<=FOX_POS+1)`
  - jump 落地后（第71行）：`if(rabbitPos>=FOX_POS&&rabbitPos<=FOX_POS+1)`
- **验证**：判定区间是 `[20, 21]`（包含 20 和 21）
- **问题分析**：
  - 跳跃期间（`t<1`）**不做碰撞检测**，只有落地后检测。这符合“跳起来躲过狐狸”的设计。
  - **但是**：从 jumpStartPos=15 起跳，落地到 20（`20>=20 && 20<=21`）→ **死亡**。从 16 起跳，落地到 21 → **死亡**。
  - 这意味着玩家必须在狐狸前 **至少 7 格（≤14）** 起跳，否则落地即死。跳跃距离 5 无法直接越过位于 20 的狐狸而不落在其判定区间内。
  - **风险评估**：速度 0.5 时，从 14 跳到 19，有 2 帧（200ms）窗口再次跳跃；速度提升到 0.6 后，只有 1 帧（100ms）窗口。**窗口极窄**，高关卡几乎必然撞死。这是一个**设计/数值平衡问题**。

## 🔴 P0 — 阻断级 Bug

### BUG-001：JavaScript 语法错误导致脚本无法执行
**位置**：第72行、第81行  
**代码**：
```javascript
btn.textContent=.🔄 重来.;     // 第72行
btn.textContent=.🔄 重来.;     // 第81行（重复出现）
```
**问题**：`.` 在 JavaScript 中不能作为字符串字面量的引号。解析器会将 `.` 视为数字字面量或属性访问的开始，导致 **SyntaxError**。整个 `<script>` 块无法执行，游戏完全无法运行。  
**修复建议**：
```javascript
btn.textContent = '🔄 重来';
```
（使用单引号或双引号包裹字符串）

## 🟡 P1 — 严重问题

### BUG-002：跳跃落地后碰撞区间过宽，导致“安全跳跃”变“自杀跳跃”
**分析**：
- FOX_POS=20，碰撞区间 `[20, 21]`（包含 20 和 21 两个格子）
- 跳跃距离=5，从 jumpStartPos 起跳，落地位置 = jumpStartPos + 5
- 安全起跳的条件：落地位置 `< 20` **或** 落地位置 `> 21`
  - 即 jumpStartPos + 5 < 20 → jumpStartPos < 15（最大14）
  - 或 jumpStartPos + 5 > 21 → jumpStartPos > 16（不可能，因为在 20 就死了）
- **结论**：玩家必须在距离狐狸 **至少 6 格** 的位置（≤14）起跳，否则落地即死。
- 这意味着跳跃距离 5 无法让玩家“跳过”位于 20 的狐狸——玩家需要提前 6 格起跳，狐狸本质上是一个 2 格宽的障碍物，而跳跃弧长只有 5 格。

**影响**：
- 速度 0.5：从 14 跳到 19，有 2 帧（200ms）反应时间再次跳跃。尚可操作。
- 速度 0.6：从 14 跳到 19，只有 1 帧（100ms）反应时间。极难操作。
- 速度继续提升后，窗口趋近于 0，高关卡几乎不可玩。

**修复建议**（任选其一）：
1. 增大跳跃距离（如 `dist=7`），确保能从 15 起跳越过 `[20,21]` 落在 22+
2. 缩小碰撞区间（如只检测 `rabbitPos === FOX_POS`，去掉 `+1`）
3. 将狐狸位置后移，或降低初始速度，给玩家更大反应窗口

## 🟢 P2 — 一般问题

### ISSUE-003：`init()` 职责不完整
- `init()` 重置了 `rabbitPos`、`posAccum`、`rabbitState`、`btn` 状态，但**不重置** `speed` 和 `level`
- 死亡重置逻辑散落在 `update()` 的两处碰撞检测中（第53行、第72行）
- 建议将死亡/通关的状态重置统一收敛到 `init()` 或专门的 `resetGame()` 函数

### ISSUE-004：`speedInfo` 未在 `init()` 中更新
- `init()` 没有更新 DOM 元素 `speedInfo` 的文本
- 当前流程中 `speedInfo` 在 win 处理时已被更新，所以视觉上看不出问题
- 但如果单独调用 `init()`（如未来扩展功能），`speedInfo` 会显示过期内容

### ISSUE-005：`endTimer` 变量声明后从未读取
- 代码中 `let ..., endTimer, ...;` 并在多处赋值 `endTimer=0`，但没有任何地方读取 `endTimer`
- 建议清理死代码，或实现其原本意图（如延迟显示/延迟重置）

### ISSUE-006：跳跃期间 posAccum 被覆盖为整数，导致落地后 walk 步进不一致
- walk 状态时 `posAccum` 是连续小数（步进 0.5）
- jump 状态时 `posAccum = rabbitPos` 被设为整数（因为 `Math.round`）
- 落地后 `posAccum = rabbitPos = jumpStartPos + dist`（整数）
- 这导致从 walk 进入 jump 时，小数部分丢失。对速度 0.5 影响小，但对非 0.5 步长可能产生累积误差

## 特别关注验证

### 关注 A：初始速度 0.5 + 狐狸位置 20 + 跳跃距离 5 → 是否合理？
**结论**：数值设计**偏紧**，高关卡容错率极低。
- 狐狸位于 20，终点 30，有效跑道仅 20 格
- 跳跃距离 5，碰撞区间宽 2 格（20-21）
- 每关速度 ×1.2，指数增长：0.5 → 0.6 → 0.72 → 0.86 → 1.04 → ...
- 速度超过 1.0 后，每帧走 1+ 格，反应时间趋近于 0
- **建议**：将速度乘数从 1.2 降至 1.1，或增大跳跃距离，或缩小碰撞区间

### 关注 B：死亡重置时速度应该回到 0.5 而非 1
**结论**：✅ **当前代码正确**
- 两处碰撞处理都设置了 `speed=0.5; level=1;`
- 但 BUG-001（语法错误）会导致整个脚本无法执行，修复语法错误后此逻辑才生效
